# GitHubの使い方（初心者向け・図解しやすい版）

## 1. GitHubって何？
GitHubは、**コードやドキュメントの変更履歴を保存して、チームで共有・レビューできるサービス**です。

- **Git**: 変更履歴を管理する仕組み（バージョン管理）
- **GitHub**: Gitのデータをクラウドで管理する場所

---

## 2. まず覚えるべき用語（最重要）

- **Repository（リポジトリ）**
  - プロジェクトの保管庫
- **Commit（コミット）**
  - 変更を「この状態で保存」と記録すること
- **Branch（ブランチ）**
  - 変更作業を分岐して進める作業ライン
- **Pull Request（PR）**
  - 「この変更を取り込んでください」という申請
- **Merge（マージ）**
  - PRの変更を本流に反映すること
- **Issue（イシュー）**
  - バグ報告・タスク・相談の管理チケット

---

## 3. 全体の流れ（まずはこれだけ）

1. リポジトリを用意する
2. ブランチを作る
3. 変更してコミットする
4. GitHubにPushする
5. Pull Requestを作る
6. レビューを受ける
7. Mergeして完了

---

## 4. 図解用：GitHubワークフロー（テキスト図）

```text
[Issueで作業内容を決める]
          ↓
[main から featureブランチ作成]
          ↓
[編集 → commit]
          ↓
[GitHubへ push]
          ↓
[Pull Request作成]
          ↓
[レビュー・修正]
          ↓
[Merge]
          ↓
[不要ブランチ削除]
```

この図をそのまま四角と矢印で描けば、初心者向け資料として使えます。

## 5. 最初の1回で使う基本コマンド

### 5-1. Gitの初期設定（PCごとに1回）

```bash
git config --global user.name "あなたの名前"
git config --global user.email "あなたのメール"
```

### 5-2. 既存プロジェクトを取得

```bash
git clone <リポジトリURL>
cd <フォルダ名>
```

### 5-3. ブランチ作成

```bash
git switch -c feature/add-login-page
```

### 5-4. 変更を保存（コミット）

```bash
git add .
git commit -m "ログイン画面を追加"
```

### 5-5. GitHubへアップロード

```bash
git push -u origin feature/add-login-page
```

### 5-6. PR作成

- GitHub画面で `Compare & pull request` を押す
- 変更内容を書く
- レビュワーを設定して作成

---

## 6. 画面で覚える操作の順番（CLIが苦手な方向け）

1. GitHubでリポジトリを開く
2. `main` から新しいブランチを作成
3. ファイルを編集（またはアップロード）
4. 画面下の `Commit changes...` でコミット
5. `Contribute` → `Open pull request`
6. 説明を書いてPRを作成
7. レビュー後に `Merge pull request`

---

## 7. PR説明テンプレート（初心者向け）

```text
## 目的
- 何を解決したいか

## 変更内容
- 何をどう変更したか

## 確認方法
- どの手順で動作確認できるか

## 影響範囲
- どこに影響するか
```

---

## 8. よくある失敗と回避策

### 失敗1: mainに直接コミットしてしまう
- **回避策**: 必ず作業前に `git switch -c feature/...` を実行

### 失敗2: 何を変更したか自分でもわからない
- **回避策**: コミットを小さく分ける（1コミット1目的）

### 失敗3: コンフリクト（競合）が怖い
- **回避策**: こまめにmainを取り込み、PRを早めに出す

### 失敗4: PR説明が短すぎて伝わらない
- **回避策**: 「目的・変更内容・確認方法」の3点セットで書く

---

## 9. チーム開発のおすすめ運用

- ブランチ命名: `feature/機能名`, `fix/バグ名`
- PRは小さく（200〜400行程度を目安）
- レビューコメントへの返信方針を決める
- マージ前に最低1人レビュー

---

## 10. これだけは守るチェックリスト

- [ ] mainへ直接pushしない
- [ ] 作業ブランチを切る
- [ ] コミットメッセージを具体的にする
- [ ] PRに目的と確認方法を書く
- [ ] マージ前にレビューを受ける

## 11. 図解の作り方（この文書を図に落とすとき）

おすすめは次の3枚構成です。

1. **概念図**: Git / GitHub / Repository / Branch / PR / Merge の関係
2. **時系列フロー**: Issue → Branch → Commit → Push → PR → Review → Merge
3. **運用ルール図**: やること・やらないこと（Do/Don’t）

色分けすると伝わりやすいです。
- 青: 開発者の作業
- 緑: 完了/マージ
- 赤: 注意ポイント（競合・main直push）
